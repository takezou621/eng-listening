依頼者・監督: Muse（このアプリの事業責任者）。あなたは実装担当です。
対象: eng-listening（ミミトレ - 英語の音が見える）/ React Native + Expo / このリポジトリ。

## 背景

- v1.0 は App Store 審査中（バージョン 1.0、ビルド 5）。あなたの変更は次版（v1.0.1 / v1.1）向けに、機能ブランチ + PR の形で用意すること。審査中の提出物には一切影響させない。
- 監督側（Muse）が全画面監査で洗い出した課題台帳があり、主要な修正は対応済み。本依頼は残りの構造改善と全体の磨き込み。

## 必読資料（作業前にすべて読むこと）

1. `docs/research/competitor-package-2026-11-22/INDEX.md` — 競合6社のリサーチパッケージ。各社の `brief.md`、`screenshots/`、`metadata.json`、`videos.md`、`articles.md`、`reference/`（9観点のインタラクション調査と比較表）を含む

3. `docs/operations.md` — 運用手順（提出・検証の型）
4. GitHub Issues #45 と #46（`gh issue view 45` / `46`）— 本依頼の主対象

## 作業範囲（優先順）

### A. レッスン画面の再構成（Issue #45）
- 聞く / 読む / 話す / スクリプト のモードを排他化し、画面の情報量を段階開示にする（原則 P1/P2/P6）
- 音変化の解説はボトムシートで提示する（常時表示のブロックをやめる）
- シャドーイングは1文フォーカス形式にする: お手本再生 → 自動で録音 → 聞き比べ、を1文ごとに完結させる。競合の手本は Speak の3段構成（`docs/research/competitor-package-2026-11-22/speak/brief.md`）とシャドテンのステップ固定（同 `shadoten/brief.md`）、スピークバディの「段階的に支えを外す」設計（同 `speakbuddy/brief.md`）
- 既に実装済みの下部固定の再生バー（前/次の文・シーク・再生/一時停止）は維持する

### B. 進捗と継続の仕組み（Issue #46 の残り）
- ストリーク救済（E16）: 連続記録が途切れた際の回復手段（週1回まで自動救済など、Duolingo のフリーズ相当）を、罰ではなく保険として設計・実装する
- 1日の目標設定: 学習時間またはレッスン数の目標を設定でき、「今日の1本」と進捗画面に反映する（ELSA のコーチ式、abceed の学習時間設定が手本）
- ライブラリのタイトル階層（E15）: 日本語タイトルと英語タイトルの主従を、競合のカード表現と比較したうえで判断し、根拠を PR に書く

### C. 全体のポリッシュ
- 全画面をルールブック §3 チェックリストで自己点検し、余白・タイポグラフィ・状態表現（空/読込/完了）の不統一を直す
- 新規の違反（D 台帳への追加が必要なもの）を作らない

## 進め方

1. 最初に実装計画を `docs/research/brushup-plan.md` として書き、範囲 A/B/C の進め方と PR 分割を示す（計画を書いたら止まらずに実装へ進む）
2. PR は論点ごとに分ける（A、B の項目ごと、C）。1 PR は 1 テーマ
3. 各 PR に必須: 変更画面のスクリーンショット（ライト/ダーク両モード）、ルールブック §3 のチェック結果、`npm run typecheck` と `npm run lint` の通過
4. シミュレータ検証の注意: ビルドは必ず `-workspace ios/app.xcworkspace -scheme app` を使うこと（`-project` 単体は Pods のモジュールマップ欠落で失敗する既知の問題）。検証用シミュレータは iPhone（Mimitore-67、UDID 5A4D4E38-A374-45C6-9412-403E865597F8）
5. マージはしない。PR を作るところまでがあなたの担当で、マージ判断は監督側が行う

## 禁止事項

- main への直接コミット
- 課金（RevenueCat まわり）、法務文言、価格、App Store 情報の変更
- 「カラオケ」の単独表記（正式表記は「カラオケ風表示」。UI・文言すべてで統一済みなので崩さない）
- 内部情報（開発用ログ、設定値、ID 類）をユーザー向け画面に出すこと（原則 P5）
- 音声が AI 生成（Google Cloud TTS）である旨の表記を弱めること

## 完了の定義

- 範囲 A と B の PR が作成され、C の自己点検結果が PR または計画ファイルに記録されていること
- すべての PR で typecheck / lint が通り、両モードのスクリーンショットで崩れがないこと
